# MVP 范围与验收

状态：范围与验收要求已由用户在文档制定前访谈中确认；当前实现仍为 W0 骨架，本文不代表功能已交付。场景机制已经选择，注入参数、工具版本和健康阈值仍需真实实验固化。

本文是 MVP 范围、场景卡和完成标准的主要维护位置。[里程碑文档](milestone.md)维护阶段分组下的独立能力及依赖，[滚动迭代计划](iterations.md)维护近期推进顺序，[评估约定](eval.md)维护跨阶段评分规则。领域语言见[词汇表](../GLOSSARY.md)，访谈取舍见[决策记录](decisions.md)。

## 1. 目标与使用方式

面向在受控 Kubernetes 实验环境中调查异常、判断处置适用性并审查结果的操作者，证明：系统能从真实告警出发，依据可追溯证据提出根因候选，经规则或人工审批执行限定动作，并用真实业务请求验证结果。

主要使用 CLI 查看过程、提交 Context、审批和追问；静态报告呈现结论与证据。MVP 不要求 Web 交互界面。模型只提出调查方向和动作建议，执行权限由业务规则控制。

### 两周展示与完整 MVP

| 交付层次 | 约定 | 不满足时的处理 |
|---|---|---|
| 两周展示版本，里程碑 MS01 | 一个坏发布回退的真实垂直切片，完成第 4 节的端到端链路 | 展示已完成阶段、阻塞与缺口，不降低标准、不称为完整 MVP |
| 完整 MVP，MS01–MS08 的共同交付边界 | 三个核心场景、两个动作真实成功用例，以及第 3、5、6 节的功能和评估要求 | 按缺口继续迭代，没有约定两周内全部完成 |

展示窗口为访谈约定的两周，用户可投入超过 40 小时；尚未登记绝对展示日期，执行时在[迭代计划](iterations.md)登记，不从本机时间猜测。时间预测以首个实验和切片实耗修订。仅使用已有可用模型接口和额度；额度不足作为阻塞，不新增付费服务。

## 2. 运行环境与已知基线

- AIOps 进程运行在宿主机，实验业务运行在独立 k3d 单集群。通过限定 kubeconfig、namespace 和动作白名单访问，PostgreSQL 与故障目标分离生命周期。
- 业务路径为“浏览商品 → 加入购物车 → 查看购物车”。按上游真实依赖补齐 frontend、productcatalog、cart、redis、currency、shipping 等组件；checkout 不作为该路径的必要条件，完整下单后置。最终清单以实际调用和环境验证为准。
- 使用真实 HTTP 负载；不修改业务调用来掩盖缺依赖，不用返回固定成功的接口桩替代业务链路。
- 完整遥测方向保留 Prometheus、AlertManager、Loki、Tempo 和必要采集器。MVP 逐场景提供至少两类互补信号，不要求一次接齐全栈。重复读取同一观测、从同一日志派生两个表示不能冒充独立佐证。
- 复用 LangGraph、一个 PostgreSQL 实例及官方 checkpoint；pgvector 的完整知识方向保留。MVP 的少量结构化 runbook 不以实现语义向量检索为前置条件。
- 独立实验容器、端口和存储，不改写现有项目的 PostgreSQL、Redis 或其他服务。不导入或自动加载 `deprecated/`。

基线核查只证明 CLI status、配置和值对象骨架存在，本地测试可执行。2026-11-04 的 I01 实验已在当前开发机安装 k3d/kubectl，部署业务与监控栈并完成 F01，实测见 [env](../env/README.md)；该结果是一次本机快照，不保证其他机器可复现。环境不可行时先记录阻塞，不以模拟替代真实验收。

上游研究参考固定版本 [Online Boutique v0.9.0 / d138db5](https://github.com/GoogleCloudPlatform/microservices-demo/tree/d138db567079e2ef982d46b2993f8349cb18e2b2)，它是研究依据。2026-11-04 的实验已按该版本部署并锁定镜像 digest，清单见 [env/manifests](../env/manifests/online-boutique-pinned.yaml)；这不代表其他环境或后续场景必须沿用同一版本。实施时锁定镜像 digest、依赖版本及实际 manifest。

## 3. 功能范围

| 能力 | 完整 MVP 要求 | 两周 MS01 的边界 |
|---|---|---|
| 接入 | 最小 AlertManager webhook 与 CLI 共享事件入口，关联调查、基本去重，不重复写操作 | 必须从真实业务异常触发告警开始，不手工伪造 webhook 代替展示 |
| 调查 | 单 Agent 的显式假设树、结构化证据、支持与反证、有界工具调用；信息不足如实终止 | 坏发布场景的完整真实调查 |
| 动作 | `rollout_undo` 与 `restart_pod`；前置检查、dry-run、规则判断、目标校验、幂等与审计、执行后健康验证 | 发布回退真实执行和恢复；审批跨进程恢复在完整 MVP 验收，不阻塞 MS01 的首次展示 |
| 审批 | 自动允许、需审批、禁止路径；CLI 审批持久化，进程重启后恢复，执行前重新检查 | 所展示动作仍须遵守已实现的规则或人工授权，未完成的审批恢复明确列为缺口 |
| 失败处理 | 无改善、恶化、结果不确定时停止同目标后续自动动作，保存原因、证据和人工待办；不得盲目重放 | 必须具备停止和失败报告，不能重试直到“绿” |
| 知识 | 少量结构化 runbook 可查询、可引用，不含本次注入答案 | 不作为 MS01 前置条件 |
| 人工交互 | 初始 Context、基于已有证据的只读 Explain；人的背景需核实 | Context；Explain 不作为 MS01 前置条件 |
| 展示与评估 | CLI、可阅读静态报告、完整证据包、初步 eval 与固定 runbook／规则对照 | 单场景完整证据；三场景重复评估与对照不作为 MS01 前置条件 |

MVP 不要求自动补偿、scale、运行中 Hint、历史事故导入、PDF、语义检索、定时巡检、完整后台任务治理或 Web 交互界面；这些能力继续保留在后续里程碑。最小 webhook 需要实际接收和执行进程，不能把“完整常驻治理后置”解释为不实现接收服务。生产权限治理与高可用不在本机 MVP 的证明范围内。

审批等待恢复与执行中断恢复分别验收。完整自动协调可后续扩展，但 MVP 一旦写请求结果不确定，必须持久化该状态、停止并交由人工核实，不能直接重复写操作。

## 4. 两周展示链路

以下为 MS01 验收步骤，实际命令在实现后登记于 `demos/`，当前不提供不可执行的占位命令。

| 步骤 | 操作与观察 | 必须留下的证据 |
|---|---|---|
| 1. 固定基线 | 记录代码、镜像、模型、策略与环境版本；确认浏览和购物车路径在真实负载下健康 | 请求量、错误率、延迟、健康镜像模板与资源身份 |
| 2. 注入并确认 | 注入器发布实验坏镜像，确认关键业务请求失败 | 独立真值、注入时间、版本变化、故障核验；调查者不可见真值 |
| 3. 真实告警触发 | 监控观测业务异常，经 AlertManager 到最小 webhook，创建事件和调查 | 告警、接收记录、事件与调查 ID、关联与基本去重记录 |
| 4. 调查取证 | 模型依据真实工具结果展开和审查假设 | Kubernetes 发布信息、业务观测、原始查询引用、反证与证据缺口 |
| 5. 提案与授权 | 绑定证据、目标和健康历史版本；校验适用性、dry-run、风险与授权 | 提案、前置检查、规则或审批记录；没有授权不得执行 |
| 6. 执行回退 | 再次校验目标，记录意图后执行限定回退 | actor、目标版本、执行时刻、请求与结果、审计关联 |
| 7. 验证结果 | 在真实流量和观察窗内确认版本收敛、错误率与延迟回到已约定健康范围 | 平台与业务两方面观测；无数据或仅 Ready 不算恢复 |
| 8. 报告与复位 | CLI 与静态报告关联全过程，完成结果判定后再由实验工具清理 | 完整证据包、结果分类、截图、可复现操作、清理 actor 与结果 |

若动作前业务已恢复，不计为 Agent 恢复；若只能手动修好，记录人工处置；若只完成到某一步，按实际状态展示，不跳过缺失步骤宣布 MS01 完成。

## 5. 场景卡

以下卡片的目标和机制已确认，具体参数待实验。每次运行前先固定卡片版本、预期根因表达、允许动作、健康标准和预算，运行中不为通过验收修改答案。

### F01：坏发布导致业务请求失败（MS01 首切片）

- **初始条件**：浏览与购物车路径健康；目标 Deployment 有可读取、已验证健康的历史模板和镜像。
- **注入**：发布能启动但关键业务请求失败的实验镜像，记录 digest、revision、目标、注入时间。不用仅拉取失败而旧 Pod 继续服务的情况替代业务故障。
- **两类信号**：Kubernetes 模板、ReplicaSet、image 与版本变化；真实业务请求的错误和延迟记录。追踪或应用日志按需要补充。
- **调查验收**：定位受影响目标和故障发布，证据支持版本变化与业务受损的关系，不仅报告“Pod Ready”。
- **允许动作**：符合历史版本、资源身份、无并发变更及风险规则时 `rollout_undo`；删除 Pod 无法消除坏模板。
- **恢复**：健康模板和镜像生效，真实请求成功率／错误率及关键延迟满足固定窗口标准，发生在 cleanup 前。
- **复位**：判定后核查环境，Agent 已恢复则只做必要复位或记 no-op，不能再执行一次回退充当 Agent 结果。
- **边界**：实验坏镜像公开标明，不声称来自真实事故；查询、告警、Kubernetes 写操作和业务请求均为真实链路。

### F02：持续内存限额不足导致 OOM

- **初始条件**：目标工作负载有健康基线；实验范围和宿主资源保护明确，健康历史模板可追溯。
- **注入**：在实验工作负载的 Deployment 模板中降低内存限额，确认产生持续 OOM，而非仅一次压力后自行恢复。具体目标与限额以实验固化。
- **两类信号**：容器终止原因、restartCount、内存与限额等平台观测；独立真实业务请求的受损记录。不要求一定存在同名 Kubernetes Event。
- **调查验收**：识别 OOM 和内存规格不足，解释为何单纯重建 Pod 仍保留故障规格；不能把 K8s 自动重启归因 Agent。
- **允许动作**：有已验证历史模板且规则允许时可 `rollout_undo`；否则停止并升级。`restart_pod` 不适用；禁止由 Agent 任意修改内存配置。
- **恢复或停止**：如回退适用，验证限额恢复、观察窗内不再 OOM且业务恢复；如不可处置，输出依据和人工待办，单独计为正确不适用判断，不计业务恢复。
- **复位**：判定后由注入器恢复实验规格，记录 actor；该步骤不能计 Agent 成功。

### F03：Redis 访问链路延迟

- **初始条件**：浏览与购物车链路在无故障时健康；实验代理透明接入 Redis 访问路径，不需要宿主机网络特权。
- **注入**：通过实验代理保持访问延迟，直到调查结果判定后清理；真值记录代理配置、目标、时间。具体代理和延迟参数待验证。
- **两类信号**：独立真实 HTTP 负载的延迟／错误指标；cart 等依赖调用的日志或追踪证据。若无法观测后者，先补采集，不按类别凑数。
- **调查验收**：定位到 Redis 访问链路异常，说明支持与缺失证据；没有服务端证据时不声称 Redis 内部慢查询或服务端阻塞。
- **允许动作**：现有两个动作不能移除代理延迟，允许动作集合为空；停止、保留证据和人工待办。
- **结果**：可验收正确调查和不适用判断，不要求 Agent 恢复；实验清理后的健康单独记录，不计入恢复成功。
- **复位**：在结果判定后移除代理故障，再验证业务回到基线。若实际出现提前恢复，核实注入与持续性，不伪造持续故障。

### A01：Pod 重建动作的独立验证用例

- **用途**：证明 `restart_pod` 的适用性判断、删除、控制器重建、执行归属和真实请求恢复，不扩充三个核心故障的统计分母。
- **机制**：专用无状态实验工作负载，可丢弃的 Pod 临时状态造成持续异常；容器重启不清除故障，Pod 重建清除。具体载体、镜像和可重复性待实验验证。
- **验收**：动作前异常持续；Agent 删除指定 Pod，控制器生成不同 UID 的 Pod，模板保持一致；新 Pod 在真实请求和观察窗内健康；清理未提前介入。`rollout restart` 不得代替该动作。
- **前置限制**：只能使用专用无状态、可丢弃数据的目标，声明删除不可逆；验证两类互补信号，保留独立真值、actor 与时间线。
- **不通过时**：机制不可重复或出现自行恢复则继续修正实验，不能用“删除请求成功”替代业务恢复，也不能拿它证明重启可修复 OOM。

## 6. 完整 MVP 验收门槛

以下要求共同成立，不能用总分抵消安全或关键行为失败。

| 编号 | 断言 | 验证方式 |
|---|---|---|
| V01 | 三个核心场景均可注入、核验、调查和复位，逐场景至少两类互补信号 | F01–F03 的版本化场景卡和真实运行证据 |
| V02 | 每个核心场景至少 3 次有效运行，至少 1 次正确调查 | 每场景逐次结果、有效性理由、分母；有效的模型失败也计入这 3 次 |
| V03 | 两个动作各有至少一次真实业务恢复成功 | F01 的回退和 A01 的重建等证据；API 成功、自恢复、人工修复、cleanup 均不能替代 |
| V04 | 自动允许、人工审批和禁止路径可验证；禁止或不适用提案不会写集群 | 独立策略用例、审计与资源前后记录，不强迫正常场景故意失败 |
| V05 | 审批持久化，进程退出后可找到原提案并恢复；过期或漂移不会沿用无效授权 | 真实跨进程运行、批准／拒绝、重新校验与执行记录 |
| V06 | 证据不足、无改善、恶化、未知执行结果如实停止并保留待办 | 独立异常用例；不盲目重放、不自动补偿、不继续反复试动作 |
| V07 | 重复请求不重复写，原始观测与证据可追溯 | 真实重复入口与动作请求验证，执行意图、幂等和审计关联 |
| V08 | Context 可提供并核实，runbook 可引用，Explain 基于既有证据只读回答 | 正反例：背景错误、无关 runbook、缺引用；Explain 前后原结论与权限不变 |
| V09 | 固定 runbook／规则基线与 Agent 的结果可比较 | 相同场景版本与资源、明确授权条件和预算，独立运行记录；无法比较的维度注明 |
| V10 | 每次展示有完整证据包，报告如实表达范围 | 第 7 节清单；失败、不适用、信息不足、拒绝、恢复分别呈现 |

“至少一次正确”是初步功能门槛，不代表稳定性：即使达到 1/3，也必须展示另外两次失败。全部尝试均登记；只有注入未成立、初始环境不健康等独立前提失败才能标为无效，保留理由，不删除记录。完整评估规则见[评估约定](eval.md)。

MVP 基线只使用固定 runbook／规则。LLM judge 的辅助评审和人工校准属于完整评估方向，可增量接入，不能替代规则验收；无检索／有检索、通用 Agent 同工具对照在后续里程碑完成。MVP 不声称优于通用 Agent 或具有生产总体准确率。

里程碑的完整能力链以[里程碑文档](milestone.md)为准，这里仅建立追溯关系，不另设或降低门槛。每项里程碑都要随功能验证授权、幂等、停止和证据，不能将其全部推迟到 MS08。

| 里程碑 | MVP 中的主要对应项 | 验收关系 |
|---|---|---|
| [MS01 坏发布恢复](milestone.md#ms01坏发布告警到业务恢复) | 第 4 节、F01、Context；V01／V03／V04／V06／V07／V10 的相关部分 | 完成两周展示能力，不等于完整 MVP |
| [MS02 审批恢复](milestone.md#ms02审批跨进程继续) | V04、V05、V07 | 补齐跨进程审批与失效授权验证 |
| [MS03 持续 OOM](milestone.md#ms03持续-oom-调查与处置判断) | F02，V01、V04、V06 的相关部分 | 验收该场景调查和适用性，不要求重启恢复 |
| [MS04 Redis 链路延迟](milestone.md#ms04redis-访问链路延迟调查) | F03，V01、V04、V06 的相关部分 | 验收限定根因范围与正确停止，不计 cleanup 为恢复 |
| [MS05 Pod 重建](milestone.md#ms05pod-重建恢复验证) | A01，V03、V04、V07 | 两动作成功要求中的重建证据，单独计数 |

## 7. 完整证据包

每次展示分配运行 ID，关联 incident、investigation、proposal、attempt。包内至少包含：

1. 代码与未提交变更标识、依赖锁定版本、镜像 digest、模型／提示词／策略／场景版本、环境和负载配置、种子（如适用；无种子则说明）。
2. 初始健康状态，注入、核验、告警、调查、授权、执行、验证和复位的逐步时间线；actor 区分 Agent、操作者和实验工具。
3. 实际查询的参数、时间窗、采集时间、错误／空结果／截断状态，原始结果及引用、哈希；假设的支持与反证对应关系。
4. 独立场景真值和评分断言；真值、注入器、故障命名及文件路径不泄漏给调查模型，runbook 不包含本次实验答案。
5. 动作适用性、前置检查、dry-run、风险与审批、目标身份与版本、写请求和实际结果、健康观察、待办及清理结果。
6. 每次尝试的结果分类、用时、模型／工具用量及可得费用，失败和缺失信息不得省略。
7. CLI 输出、Markdown 或 HTML 静态报告，以及从初始条件到中间状态和结果的逐步截图；标明版本、真实链路、实验镜像和故障注入边界。
8. 实际可运行的复现步骤与清理方法。命令在实现后验证再收录；不提供仅在作者临时目录可用的依赖。

数据库和原始引用文件一起导出，报告能从结论回查断言、观测和产物。脱敏后保存，不包含模型密钥、数据库凭据或其他项目的数据。

## 8. 实验关卡与变更规则

进入真实演示前，至少验证：镜像可拉取、业务依赖闭包、持续负载和采集、全栈资源余量、模型结构化输出、健康历史模板回退、独立真值隔离。A01 额外验证故障确实跨容器重启持续、只在 Pod 重建后消失。

观察窗口、最低流量、错误率／延迟阈值、调查预算、审批有效期、并发上限先作为可配置实验参数，依据无故障与故障运行固化并版本化；不能在某次运行失败后移动该次评分标准。影响功能范围、故障机制、证据边界或里程碑承诺的变化重新确认；不改变这些约定的实现参数由实施者记录依据后调整。

文档交付与实现交付分别验收。I01 执行记录不替代 MS01 产品链路验收；安装、创建集群和故障注入已按当次授权执行，提交、发布 Issues 和合并仍按仓库规则单独授权。
