本记录回填此前访谈与后续明确选择，区分已选方向、实现事实和未确认建议。主要依据是已有对话及 [架构](architecture.md)、[契约](contracts.md)、[阶段计划](milestone.md)；早期访谈依赖保留的会话摘要，不伪造逐字引文或未保留的选项编号。历史选择若与当前文档冲突，先标明冲突并核对，不把助手后来补写的细节当成用户决定。

“已确认”表示目标或边界已选，不表示功能已实现。当前代码仍为 W0 CLI 与值对象骨架；I01 环境与坏发布实验已完成，见 [env](../env/README.md) 与 [F01](../faults/f01-bad-release/README.md)。[contracts.py](../src/aiops/contracts.py) 已有 Incident、Hypothesis、ToolResult、Evidence、ActionProposal 和 RiskDecision 等模型，尚无调查运行、审批恢复和执行模块。

### 模型接入实测（2026-11-04）

用户在 I01 第 6 步确认采用现有网关。探测只使用最小 token 请求，共 10 次模型请求和 1 次模型目录查询，没有输出或保存密钥。

| 项目 | 实测 |
|---|---|
| 网关地址 | `http://127.0.0.1:3425`，绑定本地回环 |
| Anthropic 形状 | `/v1/messages` 可以调用，工具调用正常，但 `output_config.format` 和 `response_format` 被接受却不强制执行，冲突提示直接返回纯文本 |
| OpenAI 形状 | `/v1/chat/completions` 在冲突提示下仍返回 schema 合法 JSON，说明该端点执行结构约束 |
| 配置别名 | `mythos-magpie-1505138152` |
| 实际模型 | `deepseek-v4.1-flash`，目录显示 1M 上下文、384K 输出、支持 tools 与 reasoning |
| 工具调用 | OpenAI 风格 tools 正常，`finish_reason=tool_calls` |
| 用量 | 单次示例为 151 输入、39 输出，缓存读取 128；`list_cost` 与 `allowance` 的单位和剩余额度无法从单次响应确定 |

结论：项目客户端使用 `/v1/chat/completions`，以 JSON schema 作为结构约束，同时做客户端校验和有限重试。模型 ID 作为配置项，运行记录保存实际返回模型。一次探测不能当作长期保证。

运行栈版本建议：`langgraph` 1.2.19、`langgraph-checkpoint-postgres` 3.2.0、`psycopg` 3.3.7、`pydantic` 2.14.2，当前 Python 3.12.14 满足要求。这些版本尚未安装，checkpoint 也未验证。

## 本轮访谈已收敛的边界

用户已确认最后的整体理解并授权制定三份文档；此后确认持续 OOM 与 Redis 访问链路延迟的具体机制。决策记录保留取舍来源，功能标准只在 [MVP 范围与验收](mvp.md)维护，阶段与近期顺序分别在[路线图](milestone.md)和[迭代计划](iterations.md)维护。

| 决策 | 已确认取舍及理由 |
|---|---|
| 展示窗口 | 固定两周内展示，允许展示准确标明的中间阶段；不为日期降低验收，也不把完整 MVP 承诺压进两周 |
| 首切片调整 | 坏发布回退替代 OOM；Kubernetes 可能自行恢复一次性 OOM，持续限额不足又不能靠重建清因，不能把这些算作 Agent 重启成功 |
| 坏发布机制 | 实验镜像可启动、关键业务请求失败；不使用健康旧 Pod 持续服务的拉取失败案例冒充业务中断 |
| OOM 机制 | 使用持续内存限额不足；重建不适用，健康历史模板可回退且规则允许时回退，否则停止 |
| Redis 机制 | 实验代理保持访问链路延迟；不用自动到期掩盖结果，不声称 Redis 内部慢查询或服务端阻塞 |
| 动作验证 | 允许专用无状态实验工作负载证明 Pod 重建；故障仅在可丢弃 Pod 临时状态内，机制先实验，不能用于证明重启通治 OOM |
| 展示形式 | CLI + 可阅读静态报告，无 MVP Web 交互要求；逐步保存初始、操作、中间状态、结果和清理证据 |
| 风险与审批 | 自动／审批／禁止路径均需验证；审批绑定具体提案，持久化并跨进程恢复，目标或授权失效重新评估 |
| 失败与补偿 | MVP 对无改善／恶化／未知结果停止并持久化待办；自动补偿后置。发布回退这一处置动作不等于补偿 |
| 知识与交互 | MVP 少量结构化 runbook、Context、Explain；MS01 先 Context，知识与 Explain 不阻塞首展示；不向模型透露本次注入答案 |
| 后续顺序 | 先处置可靠性，再持续运行，之后扩展知识、故障与对照交付；完整目标不缩减，各阶段持续评估 |
| 计划维护 | 按切片验收或重要阻塞更新，只详细展开当前和下一切片；任务状态进入 GitHub Issues，发布仍需相应授权 |
| 里程碑粒度 | 用户指出原里程碑把多项完整能力归进一个大阶段，确认改为“阶段分组 → 独立能力里程碑 → 迭代任务”；采用 MS01–MS20，MVP 是 MS01–MS08 全部通过的交付边界，安全与原验收标准不后置、不降低 |

### 旧补写条款的最终处理

旧文档曾混入未确认建议，本轮没有整体追认，而是逐项选择：

| 原建议 | 最终状态 |
|---|---|
| 每场景两类信号，三场景合计覆盖全部四类 | 已确认逐场景两类互补信号；不要求 MVP 覆盖全部四类 |
| 每场景至少三次 | 已确认三次有效运行且至少一次正确调查，全部失败与无效尝试保留；不证明稳定性 |
| 风险三态和两动作成功 | 已确认覆盖风险路径、两个动作各真实成功；通过适用场景和独立测试验证，不要求每场景执行两动作 |
| 正常故障集必须至少一次拒绝或 inconclusive | 不采用；用独立危险提案／证据不足用例验证，不强迫正常场景失败 |
| 必须置信度、Top-3、种子和单条复现命令 | 不要求模型置信度或强制 Top-3；需可执行复现步骤、版本及适用时种子，不保证一条命令覆盖全部链路 |
| MVP 排除所有常驻能力 | 不采用该笼统排除：最小 webhook 必须有接收和任务运行；完整治理与巡检后置 |
