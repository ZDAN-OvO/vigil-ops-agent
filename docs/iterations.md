## 2. 当前切片 I01：证明环境与坏发布实验可观测、可复位

这是 MS01 的实验关卡，不单独宣称产品闭环完成。先验证最可能使两周计划失效的假设，再细化后续实现。

### 进入条件

已确认 MVP 场景卡；读取架构、契约和协作规则。实施开始前登记代码基线、实际展示日、实施者／核验者和实验资源范围。环境安装、部署与注入已于 2026-11-04 在本地实验环境执行，结果见 [env](../env/README.md) 与 [F01](../faults/f01-bad-release/README.md)；实施者与核验者尚未登记。

### 顺序与每步出口

| 顺序 | 工作 | 完成证据与失败处理 |
|---|---|---|
| 1 | 核对工具、已有服务、可用资源和镜像网络；设计独立集群、namespace、存储与端口 | 固定版本／digest 和资源清单；不改动或停止其他项目服务，下载或资源受阻先登记 |
| 2 | 建立最小真实业务依赖与 HTTP 负载，逐步增加必需组件 | 浏览、加购、查看购物车成功；记录 CPU、内存、启动耗时和请求量；不能只看 Ready |
| 3 | 建立平台与业务观测，验证 Prometheus／AlertManager 及所需采集 | 查询可回查原始观测、时间窗有效；触发真实业务告警。按场景需要接日志或 trace，不抢先接齐全栈 |
| 4 | 固定健康镜像和实验坏镜像，验证发布能造成业务请求失败 | 版本变化、故障核验、两类互补信号和独立真值；若旧 Pod 继续服务不能算故障成立 |
| 5 | 由实验操作者验证回退与复位，固定健康观察规则 | 真实请求受损→回退→恢复，且重复可运行；这是实验可行性证据，不计 Agent 处置成功 |
| 6 | 验证现有模型的连通性和结构化输出，确定最小运行栈版本 | 最小调用结果、错误行为和用量，不输出密钥；复用成熟依赖，不自建通用编排运行时 |

步骤 5 的操作者回退仅用于验证场景和适配条件，必须与后续 Agent 实际回退使用不同运行记录。注入器可修改实验镜像和规格，不意味着调查 Agent 获得任意配置写权限。

## 3. 下一切片 I02：把实验链路接成可审查的 Agent 发布回退

依赖 I01 的环境、场景、健康判定和版本信息。I01 退出后再细化节点、schema、迁移和任务负责人，以下为先后依赖与出口，不是预分配工单。

I01 已提供 OpenAI 兼容模型端点、结构化输出行为、版本建议、F01 探针与告警规则，以及真实回退耗时。仍未提供 PostgreSQL 与 checkpoint 验证、正式场景接口和真值隔离；这些是 I02 的前置或首步工作。

1. **先对齐持久化与工具边界**：基于已有值对象补齐调查、调用、提案、执行意图和审计的最小状态与迁移；接官方 LangGraph checkpoint。确认查询输出、原始引用、预算／超时和错误边界。
2. **先跑通 CLI 只读调查**：Context → 真实有界取证 → 假设与反证 → 根因候选或信息不足 → 报告；测试背景错误或查询失败时不编造。
3. **连接真实告警入口**：AlertManager → webhook → 事件／调查；关联 CLI 查看，基本去重，并把取证与告警放在同一运行记录中。
4. **加入受控回退**：前置条件、dry-run、规则或明确人工授权、再次校验、目标互斥与幂等意图 → 回退 → 真正的业务验证。未知执行结果停止待核实，不能盲目重放。
5. **完成 MS01 证据报告**：按 [MVP 展示链路](mvp.md#4-两周展示链路)从头运行，留初始、操作、中间状态和结果截图，覆盖必要的重复请求／失败停止；所有失败列出。

I02 出口：MS01 的整条展示链通过，告警、模型调查和集群动作均为真实行为。审批跨进程恢复、runbook、Explain 和完整三场景 eval 分别在 MS02、MS06、MS07、MS08 交付，展示中明确当前缺口；不得省略 MS01 授权、幂等和结果核实。

## 4. 两周展示准备与调整

不把未知实验工时拆成虚假的每日承诺。使用三个证据检查点：

| 检查点 | 核对内容 | 计划调整 |
|---|---|---|
| I01 出口 | 环境与坏发布机制是否成立，模型与工具是否可用，实际耗时多少 | 形成 I02 的任务依赖、剩余工作与时间预测；未过关先修前提 |
| I02 集成 | 告警到真实业务恢复是否连通；授权、幂等和失败状态是否准确 | 修复具体阻塞，不扩展额外功能；保留运行历史 |
| 展示前 | 按干净初始条件复现、检查报告引用与截图、执行复位 | 只展示证据支持的阶段；如 MS01 未完成，列出缺口而非改验收标准 |

执行启动时填写实际展示日期与检查安排。若检查点显示延期，允许调整顺序或展示中间阶段；改变范围和故障机制需说明并确认，不以降低断言或删除失败换取通过。

| MS02 审批跨进程继续 | 在 MS01 提案上先验证等待→退出→重启→批准／拒绝，再加过期、漂移与重复批准，不另建审批系统 | [MS02](milestone.md#ms02审批跨进程继续) |
| MS03 持续 OOM | 先证明 F02 注入与业务受损，再复用调查工具解释资源规格、判断重建无效，条件允许时回退或停止 | [MS03](milestone.md#ms03持续-oom-调查与处置判断) |
| MS04 Redis 链路延迟 | 先验证代理延迟持续及两类信号，再复用证据与停止链路；结果判定后才 cleanup | [MS04](milestone.md#ms04redis-访问链路延迟调查) |
| MS05 Pod 重建 | 先实验 A01 故障只在 Pod 重建后消失，再接已有授权、执行、UID 与真实请求验证 | [MS05](milestone.md#ms05pod-重建恢复验证) |
| MS06 Runbook 调查 | 先用少量可审查条目完成查询→核实→引用，再加错误／无关条目反例，不先建大规模知识平台 | [MS06](milestone.md#ms06runbook-辅助调查) |
| MS07 只读追问 | 直接复用持久调查与 evidence 引用，实现 CLI 提问→回答／缺证据说明，并证明无额外查询和写操作 | [MS07](milestone.md#ms07调查结果只读追问) |
| MS08 重复评估 | 复用各里程碑运行记录，冻结规则基线及评分；补齐重复次数、安全与异常用例，核对 V01–V10 全部通过 | [MS08](milestone.md#ms08重复评估与规则基线)、[MVP 门槛](mvp.md#6-完整-mvp-验收门槛) |

## 6. 每轮维护规则

每次切片验收、关键假设被证伪或出现重要阻塞时更新本文：当前能力、验收证据、实际用时、阻塞／返工、当前切片和下一切片。仅更新进度时不重写 MVP 范围。

- **主要维护位置**：MVP 维护范围和场景标准，里程碑文档维护阶段分组下的独立能力与依赖，本文维护近期顺序，GitHub Issues 维护执行任务、依赖、负责人和状态。链接引用，不复制四份进度清单。
- **任务发布**：本轮没有发布 Issues。获准后按[协作规则](agents/issue-tracker.md)创建，包含目标、前置依赖、契约、失败路径、验收命令、真实证据及实施／核验者；未关闭阻塞不视为可启动。
- **参数调整**：实现者可用实验决定版本、窗口、预算等默认值，登记依据并在运行前冻结。改功能范围、故障机制、恢复含义或证据要求时重新确认。
- **验证**：代码变更运行根目录 `make check-all`；基础设施与写操作另附真实运行证据。测试、回放和真实环境标识清楚，不用总测试数代替功能链路。
- **并行与串行**：契约先对齐，写入使用独立 worktree；同一环境的故障注入、动作和集成验收串行。每个切片登记一名实施者和一名核验者，人员未定时如实留空。
- **授权**：文档确认不等于安装、共享资源变更、付费、发布、提交或合并授权；按当前任务和仓库规则执行，不从计划表推定权限。
