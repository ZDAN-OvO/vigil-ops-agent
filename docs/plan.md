## 本轮的适用边界

- **本轮是探索性批次**：协议与词表在运行期间成形并落盘，事后没有改动门槛或阈值，但
  Git 时间不能证明"跑之前就冻结"。记录里的代码锚点（`git_head`、提示词指纹、场景脚本
  sha256、三个运行时版本）是评审后补采的，运行时的实际值无法回溯确认。因此结论只作方向
  判断；下一批必须先在冻结的 SHA 上开跑（[ADR-0013 6.1](adr/0013-comparative-evaluation.md#61-时序诚实性)）。
- **3 次样本里差 1 次不足以支撑强弱**：结论里同时给出绝对次数（如 `2/3 vs 3/3`）。门槛
  只约束"够不够比较"，不保证"差一次就是能力差距"。
- **排除的 3 次运行留在记录里**：第一版通用 Agent 臂误删了委派能力，与臂定义不符；
  这 3 条以 `valid=false`、`invalid_reason=protocol_mismatch` 保留在 JSON 中，不计入分母，
  不被新运行覆盖。

## 未完成状态与依据

- **规则形状的故障集偏向规则基线，第一轮已经证实**：2026-11-18 的对照里规则臂 13/13
  诊断正确、零越界，Pod 重建的中位耗时是 Agent 臂的 42%（178s vs 423s）、Redis 延迟是
  1%（2.3s vs 197s）。按决定 5 的口径，这两格"支持相对收益结论"——但收益属于规则基线，
  不是 Agent。这个结果说明基线有效、故障集偏规则形状；要证明方法论收益，必须先扩一个
  规则覆盖不到的故障形状。
- **样本仍然是单机小样本**：同一模型、同一实验环境、单节点 k3d。门槛只约束"够不够比较"，
  不构成生产可用性或总体准确率的证据。
- **需要审批的动作不计恢复**：`f01` 的 `rollout_undo` 在 `vigil-shop` 需要人工审批，
  三条臂同等停在 `waiting_approval`。这些场景比较的是"提案是否正确"，恢复由批准方完成，
  不记任何一臂的恢复成功。
