# ADR-0008：产品范围、实验环境与故障集

- 状态：已采纳（2026-11-14 由原决策记录合并）
- 相关：[ADR-0004](0004-controlled-resource-actions.md)、[ADR-0007](0007-skill-tool-subagent-runtime.md)、[全局架构](../../ARCHITECTURE.md)

## 背景

Vigil 面向中小企业和个人开发者，做事件驱动的故障调查与受控处置。范围、运行环境和故障集需要先固定，验收才有共同的前提。

## 决定

1. **产品范围**：故障调查、规则为主的风险分级处置、执行后业务验证，以及有边界的自动补偿。完整范围不缩减，按可独立验收的能力逐项推进，可靠性优先。
2. **相对通用 Agent 的收益**：必须用调查效果、恢复结果和操作边界来证明，不能以“通用 Agent 做不到触发、持久化或策略控制”为依据。这项证明在对照评估重建后进行。
3. **运行环境**：Vigil 运行在宿主机；业务运行在独立的 k3d 单节点集群，使用 Online Boutique v0.9.0 的浏览、加购、查看购物车路径，镜像按 digest 锁定。实验用的 PostgreSQL、端口和存储独立，不复用或改写宿主上其他项目的服务。
4. **遥测**：完整目标是 Prometheus、AlertManager、Loki、Tempo 加必要采集器。当前接入 Prometheus、blackbox-exporter、kube-state-metrics 与 AlertManager。每个场景至少有两类互补信号；同源派生的信号不算独立佐证。
5. **工具接入**：用 Python client 或 HTTP 直连遥测与 Kubernetes，MCP 不进入关键路径。
6. **故障集**：完整目标是资源、依赖、配置发布、网络四类共 12 个场景，每个场景可注入、核验和复位，不引入 Chaos Mesh。当前的核心场景是坏发布、持续 OOM、Redis 访问链路延迟；Pod 重建是独立的动作验证场景，不计入核心场景的分母。
7. **触发**：AlertManager webhook 与 CLI；定时巡检后置。告警只触发调查，不授权写操作。
8. **知识**：当前只提供少量结构化 runbook 的查询与引用；历史事故、文本 PDF 与向量检索后置。
9. **交互界面**：CLI 加报告；前端与持续对话后置。

## 后果

- 单机实验结果不证明生产可用、高可用、企业权限治理或总体准确率。
- 新增故障场景前，要先写明机制、两类信号、可接受结论与复位方法，再进入验收。
- 场景真值不进入调查模型可读范围；具体边界见[故障目录](../../faults/README.md)。
