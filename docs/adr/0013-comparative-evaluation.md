# ADR-0013：对照评估的方法、判定口径与门槛

- 状态：已采纳（2026-11-18）
- 取代：[ADR-0007](0007-skill-tool-subagent-runtime.md) 中"规则基线与完整验收评分器移出本阶段"的处置；要求本身按本 ADR 重建
- 相关：[ADR-0008](0008-product-scope-and-lab.md)、[ADR-0009](0009-risk-verification-and-stop.md)、[ADR-0011](0011-investigation-budget.md)、[故障目录](../../faults/README.md)、[阶段计划](../plan.md)

## 背景

阶段计划只剩一件事：证明相对规则基线和通用 Agent 的收益。但它有两个前置条件在仓库里
没有落地——"新数据模型稳定"没有完成判据，"场景评分与对照方法"完全不存在。ADR-0007
当时移除了规则基线和验收评分器，所以现在既没有基线可跑，也没有口径可判。

更麻烦的是顺序：如果先跑实验再定口径，看到结果之后调整词表或门槛，等于自证。因此本
ADR 先把臂的边界、判定维度和门槛写死，再让实验去撞它。

## 决定

### 1. 三条臂共用同一套环境与记录

| 臂 | 运行时 | 与其它臂的差异 |
|---|---|---|
| `agent` | `create_agent` + Skill 目录 + 排查方法提示词 | 现状能力 |
| `generic` | 同一个 `create_agent` 循环，去掉 Skill 与排查方法提示词 | 只有方法论与 Skill 被移除 |
| `rules` | 固定规则链，不调用模型 | 只有判定方式被替换 |

三条臂共用只读工具、工具账本、观测表、假设与证据关系、动作提案、风险规则与执行器，
并且都写同一份 `investigations` / `proposals` / `attempts` 记录。因此差异只能来自
"怎么得出结论"，不能来自"能不能写集群"或"有没有被审计"。委派调查也三条臂都有：
`generic` 只是不在子调查里加载 Skill。

**边界说明**：动作治理（风险分级、审批、验证、幂等）对三臂完全相同，所以本对照**不**
证明治理带来的收益，只证明方法论与 Skill 的增量。相对外部通用 Agent 的对照不在此列，
需要外部 Agent CLI 与独立预算，见"后果"。

### 2. 场景接口统一为四个动词

`faults/<场景>/repeat.sh` 必须提供 `preflight`、`inject`、`verify`、`recovered`、
`cleanup`：

- `preflight`：健康基线与所有权检查，不改变集群；
- `inject`：注入故障并等到故障成立；
- `verify`：确认故障仍然成立；
- `recovered`：只读检查业务是否已恢复，**不做任何修改**；
- `cleanup`：复位到健康基线。

每个动词的最后一行是机器可读结论：`RESULT verb=<动词> ok=<0|1> k=v ...`。缺这一行、
退出码非零或 `ok=0` 都判该步失败。

故障机制、参数与安全判断仍只写在场景脚本里（单一权威来源）。Python 侧只做编排与解析：
如果评估代码直接调 `kubectl`，就会出现两套会各自漂移的故障实现。

### 3. 有效运行

一次运行只有在**健康基线成立、注入成立、故障核验成立**时才算有效。只有独立前提失败
（例如注入没生效、基线本来就不健康）可以判无效，并必须写明原因。臂自身的失败——预算
耗尽、结论错误、动作被拒——一律计入分母，不被后续成功覆盖。

### 4. 判定维度

| 维度 | 判据 | 数据来源 |
|---|---|---|
| 诊断正确 | 结论命中词表 **且** 支持观测覆盖必需证据检查 **且** 动作决策无误 | 结论、假设、观测、工具请求 |
| 正式确认 | `investigation.conclusion` 非空 | 调查记录 |
| 动作决策 | 该动作时提出正确动作与目标；该停止时 0 提案 | 提案记录 |
| 本臂恢复 | 存在 `verified` 且 `improved` 的执行尝试 | 执行记录 |
| 边界越界 | 场景不允许的动作种类、命名空间外目标、该停止却提案 | 提案记录 |
| 成本 | 墙钟、工具调用、模型调用 | 工具账本与任务记录 |
| 人工介入 | 非 `policy:` 来源的审批、遗留待办 | 审批与待办表 |

必需证据检查由两部分组成：工具名（有没有真的看过这类对象）和事实判定（观测取到的值
是否真的异常，例如 `probe_success < 1`、`last_terminated.reason=OOMKilled`、日志出现
5xx），外加标签作用域（观测必须指向本场景的探针 `probe_*{job="frontend-probe"}`）。
只看查询名不够：表达式可以随便写，值不能随便编，也不能拿别的 job 的异常充数。

成本与人工介入三项（工具调用、模型调用、非 `policy:` 审批）进汇总表并参与"没有任何维度
更差"的比较；任一条臂有样本缺耗时，则该维度记为不可比，不允许拿剩下的样本算中位。

三处刻意保守：

- **结论用词表判断**。判定文本优先取正式结论；只有当正式结论为空时，才取状态为
  `supported` 的假设陈述（`pending` 的候选不算诊断）。两者不拼接，否则错误结论能靠
  一条旧假设刷成正确。带否定词的片段（"已排除 X"）不计命中。措辞与词表不符、但证据和
  动作都正确时，不直接判"诊断错误"，而是记 `needs_review` 交人工复核。宁可低估，
  不把会说话的臂算成更聪明。
- **动作只看本场景允许的处置**。期望动作之外还处置了其它目标（诊断目的的探测除外），
  记越界并判动作决策错误；不是"有一条对的就算对"。
- **平台侧状态不只认一种查法**。`kubernetes.list_pods` 与 `kubernetes.list_events` 都能
  证明"Pod 没有重启/驱逐"，只认前者会把"用事件流取证"的调查误判成没证据。
- **结论要落在同一个肯定片段里**。所有关键词必须同现于一个片段才算命中；词齐全但分散
  在不同片段（"Redis 正常，延迟来自 CPU 饱和"）时不判错也不给分，记 `needs_review`，
  避免用半句正确的话盖住因果说反的结论。
- **证据只认没有被推翻的假设**。状态为 `refuted` 的假设留下的 supporting 关系不算证据；
  存在 `supported` 假设时只取它的证据。
- **需要审批的动作不代批**。三臂同等停在 `waiting_approval`，恢复由人完成；
  因此这类场景只比较"提案是否正确"，不比较"是否恢复"。

### 5. 门槛（跑之前定死）

- 每个（场景，臂）至少 **3 次有效运行**才计入比较；
- 诊断正确率不低于 **2/3**，且边界越界为 **0**，才算该臂在该场景达标；
- 一个臂必须在某个维度上更好且**没有任何维度更差**，才能宣称相对收益；
  否则本轮明确写"不构成对照结论"，不允许用单场景或单次成功代替。

### 6. 判定可重算

`aiops lab rescore` 按当前口径重算既有记录，不重跑实验。改词表或门槛后必须重算并
重写记录，不允许只在新实验上生效。

重算只用记录里的 `facts.snapshot`（结论、假设、支持观测、提案、尝试、成本的完整快照），
不回头读数据库——实验之后的审批、恢复或清理都不能改写历史结论。没有快照的老记录在首次
重算时补采一份，并标注 `snapshot_source` 与 `snapshot_captured_at`。

### 6.1 时序诚实性

本轮的协议与判定词表是在运行期间逐步成形并落盘的：ADR-0013 首次提交的时间晚于部分运行
结束。数值门槛与规则阈值在实验后的提交里没有被改动过，但这**不足以证明运行前已经冻结**。
因此本轮记为**探索性批次**，结论只作为方向判断；下一批实验必须先把协议版本、执行版本和
门槛提交成不可变锚点，再开跑。

记录里为此带了代码锚点：`git_head` 与是否有未提交改动、模型名、两套提示词的指纹、三个
运行时版本、每个场景脚本的 sha256。锚点只能证明"记录对应哪一版代码"，不能证明"跑之前
就冻结"——所以还要靠下一批在干净 SHA 上跑，再对照这份记录。

**结论同时给绝对次数。** 每格只有 3 次，`2/3` 与 `3/3` 只差一次运行；支配关系成立
不等于能力差距成立。汇总里每条比较写成 `2/3 vs 3/3`，读者自己判断这点差异够不够。

### 7. 规则基线（冻结规则集）

规则集与阈值在代码里公开（`src/aiops/investigation/rules.py`），运行前冻结：

| 规则 | 触发条件 | 决策 |
|---|---|---|
| R1 发布回归 | 当前 revision 的镜像与更早 revision 不同、Pod 在窗口内重启、入口成功率归零 | 提案 `rollout_undo` |
| R2 规格不足 | `last_terminated.reason=OOMKilled` 且重启 ≥ 3 且模板内存限额 ≤ 64Mi | 判定 + 人工待办，不动作 |
| R3 依赖链路 | 入口延迟 ≥ 300ms、Pod 全就绪、重启 0、镜像未变；若发现 Service 选择器指向别的工作负载则点名 | 判定 + 人工待办，不动作 |
| R4 Pod 局部状态 | 镜像未变、Pod 就绪、重启 0、入口未失败、目标日志出现 5xx | 提案 `restart_pod` |
| R5 未命中 | 以上都不成立 | `inconclusive`，不猜 |

阈值改动等于换一条基线：改之前先改本 ADR，并按决定 5 重跑全部对照。

### 8. 场景脚本的复位契约

`preflight` 名义上只读，但 A01（Pod 重建）需要在预检阶段先把健康版本部署出来，属于
场景规格里声明的例外（`preflight_creates`）。为避免"预检失败却删掉别人的资源"，脚本在
`RESULT` 行里自报 `created=0|1`：只有自报创建过，编排才会在失败后复位。其余三个场景的
预检是纯只读的。

## 考虑过的选项

- **用模型做裁判（LLM judge）评结论**：与"证明模型能力"的目标同源，难以排除裁判偏好；
  且不稳定、不可回查。留作后续辅助评审，不作为主判据。
- **只人工评审、不做机器判定**：无法支持多次重复与跨臂比较，也容易被"看结果再定标准"
  污染。人工评审保留在 `needs_review` 这一层。
- **把规则基线实现成另一个 Agent 循环**：那就不再是规则基线，无法回答"没有模型会怎样"。
- **让 `generic` 臂也去掉动作工具**：会同时移除治理能力，混淆"方法论"与"操作边界"两个变量。

## 后果

- 单机、同一模型、同一实验环境的小样本只支持初步结论，不证明生产可用或总体准确率。
- 词表判定可能低估措辞不同的正确结论；每次 `needs_review` 都要在运行记录里人工核对。
- 规则集与现有四个场景耦合（它们本来就是按 runbook 设计的），在规则形状的故障集上
  规则基线容易打平；这本身应作为结论写出来，而不是隐藏。要证明方法论收益，需要扩展
  规则覆盖不到的故障形状。
- 相对外部通用 Agent（不是同一循环去 Skill）的对照仍未完成，依赖外部 Agent CLI 与
  独立预算评估，不在本 ADR 范围内。
- `generic` 臂与 `agent` 臂共用 `create_agent`，模型相同；换模型必须重新跑并记录在案。
- 规则臂是同步运行，没有 checkpoint：它的提案要人工执行时由操作者用 `aiops act` 重新
  提案，`approve` / `resume` 对规则臂调查直接拒绝，不猜测恢复语义。
