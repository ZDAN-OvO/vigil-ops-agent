# Pod 重建手动调查：2026-11-17

本轮补充手动入口的真实验收，验证事件观测补充对象 UID、提示词与 Skill 增加时序约束后，模型能否按 description 自主选择 `pod-rebuild`，分别确认场景诊断、正式报告与业务恢复。故障机制与真值见[场景说明](../README.md)，所有有效调查均计入分母。

## 条件与方法

- 运行时代码分三段：运行 1–3 为 `eb3b44f6779b5092f19291581cebd09d9acf3ce3`；运行 4 为复审修复后的 `cfed30482cf5ceb4fd13a41f12ef2a2818ba0725`；运行 5 为动作依据提示修复后的 `df9d93e78de3187383c0f9b4097ee01b008b40ae`。
- 本机 `vigil-lab` K8s 实验集群，目标 `vigil-experiment/rebuild-demo`，单副本、无状态、带可丢弃标签。模型请求名 `auto/deepseek-v4.1-flash`，网关 `127.0.0.1:3425`。
- 每轮先 `cleanup` 删除命名空间，再 `deploy` 重建，避免上一轮 Pod 与事件留在回看窗内。部署后确认 `/work` 为 200，再 `inject` 注入故障，`verify` 默认观察 60 秒。
- 五轮均以相同的中性症状发起 CLI 调查，无告警名、无 `--context`，不提供故障文件位置或真值，不强制加载 Skill；仍使用默认预算：工具 28、模型 20、调查 600 秒、动作 450 秒。运行 1–3 之间不改变代码；运行 4、5 的代码变化见下文“第 4 轮的失败与修复”。

```bash
bash faults/a01-pod-rebuild/repeat.sh cleanup
bash faults/a01-pod-rebuild/repeat.sh deploy
bash faults/a01-pod-rebuild/repeat.sh inject
bash faults/a01-pod-rebuild/repeat.sh verify
aiops investigate --namespace vigil-experiment --service rebuild-demo \
  --symptoms 'rebuild-demo 的 /work 持续返回 500，Pod 显示 Running/Ready；请调查原因并按规则处理。' \
  --output json
```

Prometheus 在五轮调查中均不可用（`ConnectError`），模型把它记入人工待办。本场景的两类信号是 `kubectl` 平台状态与宿主请求循环，不依赖 Prometheus；这一缺口不影响故障核验与恢复判定，但入口指标证据仍缺失。

## 第 4 轮的失败与修复

第 4 轮在 `cfed304` 上运行，故障核验成立（60 秒 59/59 失败），模型也形成了正确的 Pod 局部状态假设，并用 3 条支持观测支撑它。但它请求 `restart_pod` 时引用了 `obs-ecaecd772442`，这条观测是对 Service 假设的 refuting 关系，不是对 Pod 假设的 supporting 关系；运行时连续两次拒绝后以 `ungrounded_action` 终止。

直接原因是模型选错 evidence id；设计缺口是错误信息只说明“这条不成立”，没有列出当前可用的支持观测，模型没有足够信息自我纠正。修复后，`_validate_action_references` 在拒绝时列出该假设当前可用的 supporting 观测，并标注被引用观测的实际关系；新增回归测试。运行 5 在 `df9d93e` 上通过，说明模型能根据该提示改用有效观测。

## 与 2026-11-15 的差异

- 2026-11-15 第 3 轮把上一轮重建事件与本轮再次注入后的 500 连成同一次恢复对照；本轮每轮重建命名空间，历史事件不会进入回看窗。
