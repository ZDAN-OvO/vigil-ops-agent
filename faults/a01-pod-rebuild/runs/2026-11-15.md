# Pod 重建手动调查：2026-11-15

本轮验证手动入口能否由模型按 Skill description 自主选择 `pod-rebuild`，并分别记录场景诊断、正式报告与业务恢复。故障机制与真值见[场景说明](../README.md)，所有有效调查均计入分母，不删除失败或未确认的结果。

## 条件与方法

- 运行时代码基于 `d5061ae4ad21ff9c233e8e74f1f8eda849b5f0ea`；本轮 description 与离线回归切片为 `c57b4513c7fdb03c37da2cd977e2b806c61b0637`。没有改加载机制、触发元数据、业务逻辑或预算。
- 本机 `vigil-lab` K8s 实验集群，目标 `vigil-experiment/rebuild-demo`，单副本、无状态、带可丢弃标签。模型请求名 `auto/deepseek-v4.1-flash`，网关 `127.0.0.1:3425`；Prometheus 通过操作手册中的本地转发访问。
- 每轮先确认 `/work` 为 200，再用 `repeat.sh inject` 注入故障，`repeat.sh verify` 默认观察 60 秒。故障观察期 Pod UID 与重启次数不变、业务请求全部 500，排除观察期内自动恢复。没有重新验证容器重启对照；该机制的既有证据见场景说明。
- 三轮均以相同的中性症状发起 CLI 调查，无告警名、无 `--context`，不提供故障文件位置或真值，不强制加载 Skill；仍使用默认预算：工具 28、模型 20、调查 600 秒、动作 450 秒。轮次之间不改变 description。

```bash
bash faults/a01-pod-rebuild/repeat.sh inject
bash faults/a01-pod-rebuild/repeat.sh verify
aiops investigate --namespace vigil-experiment --service rebuild-demo \
  --symptoms 'rebuild-demo 的 /work 持续返回 500，Pod 显示 Running/Ready；请调查原因并按规则处理。' \
  --output json
```

## 第 3 轮的时序误判

三轮沿用同一个工作负载，默认取证回看 15 分钟，K8s 事件会保留前两轮的重建。第 3 轮观测 `obs-58c3b2db90b8` 对应的事件显示上一轮 05:32:49（UTC）发生过重建，模型又看到当前 Pod 在 05:37 后返回 500，就推断“重建后故障持续”。注入记录实际显示：新 Pod 在 05:37:03 注入前 `/work=200`，随后再次写坏状态文件；这两段现象不能直接构成同一次故障的恢复对照。模型因此错误反驳局部状态假设、支持应用层缺陷，花满 28 次工具预算后以信息不足结束。

这次运行已经正确选中 Skill，失败发生在后续证据时序判断，不能算成“未触发 Skill”，也不能为了选中率而剔除它。本轮不改变加载方式、运行时推理逻辑或默认预算；未继续追加运行替代该失败。
